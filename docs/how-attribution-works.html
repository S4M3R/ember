How Ember attribution works

counterfactual ablation, scored by log-likelihood drop on Nemotron

The question "which prompt block caused this response?" is a counterfactual: if I remove a block, how much less likely does the model's actual reply become? A big drop means that block was doing the work.

1. The attribution algorithm

Score the real reply once with the whole prompt, then once with each block knocked out. Biggest drop wins.

2. How each score is computed (the vLLM echo trick)

No text is generated. echo=true, max_tokens=0 makes vLLM do a single forward pass and report the log-probabilities of tokens that are already there. That is why K+1 scorings finish in about a second instead of K full generations.

sequenceDiagram
    participant A as attribute.py
    participant N as Nemotron client
    participant V as vLLM /v1/completions
    Note over A,V: Goal = logP(R | prompt_variant), no generation
    A->>N: response_loglik(prompt, R)
    N->>V: echo(prompt only)
echo=true, max_tokens=0
    V-->>N: tokens[] for prompt
    Note right of N: boundary = number of prompt tokens
    N->>V: echo(prompt + R)
echo=true, max_tokens=0
    V-->>N: token_logprobs[] for whole sequence
    N->>N: sum token_logprobs[boundary:]
= logP of response tokens
    N-->>A: scalar log-likelihood

4. Honest caveats

  • It scores the log-likelihood of the exact response string, not the failure behavior. "Issued a refund" is a behavior; we attribute a specific sentence.
  • Single-block leave-one-out misses interactions: blocks change how each other read.
  • Ablation breaks prompt coherence, and text-completion scoring only approximates the chat-template probability. Consistent across ablations, so the ranking holds, but it is a directional proxy, not a causal proof.
  • Drops are small and the load-balanced fleet adds noise (why ROLE/TONE swap run-to-run).

Planned upgrade: a second Cekura-gated mode — ablate a block, re-run, does Cekura still fail? That attributes the behavior instead of the string.
